`WriteCallbacks` is a trait rather than a structure of function pointers.
The three fields are methods taking `&mut self`, so the callbacks reach
whatever the implementation holds, and `LogWrite`'s default type parameter is
`()`, which is a writer with no callbacks at all.

**This breaks every Rust caller that passed callbacks**, which is why it is a
minor version: a caret requirement on 0.2 does not match 0.3, so nobody is
upgraded into the break. 0.2.8 is the release to upgrade through -- it added
the trait under its old name, `WriteHandler`, and deprecated the structure, so
the compiler names every site there and only the name changes here. Existing
callback functions need not be rewritten: a structure whose methods call them
is enough.

**Both a Rust and a C interface are available, and this release breaks only
the Rust one.** The `tcslog` crate is the Rust interface; `tcslog-c` is a C
ABI over the same library, with its header at `tcslog-c/include/tcslog.h`.
A C caller is unaffected by the change above: callbacks reach C through a
`TcslogCallbacks` structure of three function pointers and the `void *ctx`
handed back to each, passed to
`tcslog_write_open`, and neither that structure nor any function signature
moved -- the header is byte for byte what 0.2.8 shipped. The binding
implements the Rust trait once, over whichever C functions a writer was opened
with, so the trait is what changed underneath an interface that did not.

The C interface is there because the code producing telemetry on a flight
system is often C, and a library that code cannot call is one that does not
get used where the data is. Which to use is therefore a question of what the
caller is written in rather than of capability: `tcslog-c` presents
`LogWrite` and `LogRead` to C, so writing, reading, the recovery a damaged
log needs and the callbacks are all reachable from either side. It is a
separate crate because a C interface has to be built as a `cdylib` and a
`staticlib`, which a crate cannot be conditionally, and
because the `unsafe` an ABI needs is then confined to it -- the library crate
contains none. crates.io carries the Rust crate alone, so the C side is built
from a checkout: `make install` puts the header and both libraries under
`PREFIX`, and `cc prog.c -I$HOME/include -L$HOME/lib -ltcslog_c` links a
program against them.

Stored format: unchanged, 0.1.0. A reader of this build reads a log written
by any 0.1.x or 0.2.x build, and the other way round: the crate version and
the stored format move independently, so an API that breaks says nothing
about the logs already written.

### Removed

- `WriteCallbacks` as a structure of function pointers. The name now belongs
  to the trait that was `WriteHandler` in 0.2.8, with the three fields as
  methods taking `&mut self`, so the callbacks reach whatever the
  implementation holds. There is one way to say this again rather than two.

  **This breaks every caller that passed callbacks**, which is why it is a
  minor version. Each change is mechanical:

  | 0.2.x | now |
  | --- | --- |
  | `WriteCallbacks::default()` | `()` |
  | `WriteCallbacks { send: ship, ..default() }` | a struct with `impl WriteCallbacks { fn send(&mut self, ..) }` |
  | all three fields set | one struct implementing all three methods |
  | state in a `static` | fields on that struct; pass `&mut it` to read them after the log closes |

  A caller that wants to keep its existing functions need not rewrite them:
  a struct whose methods call them is enough, which is what the suite's own
  `Fns` helper is -- the three function-pointer fields the old structure
  had, with an `impl` that calls them. That kept twenty-four call sites in
  `api.rs` as they were.

  `0.2.8` is the release to upgrade through: it added the trait under its
  old name and deprecated the structure, so a caller can move to the trait
  there, with the compiler naming every site, and then come here for the
  rename.

- `WriteHandler`, as a name. It existed in 0.2.8 only, as the trait this
  release renames. Anyone who adopted it there renames the trait in their
  `impl` and their imports; nothing else about it changed.

### Changed

- `LogWrite`'s default type parameter is `()` rather than the removed
  structure, so `LogWrite` named without one is a writer with no callbacks.
  The documentation of the callbacks moves with the methods: what each one
  is obliged to do, and the whole account of what `send` must leave behind,
  is now on the trait rather than on the structure's fields.

### Fixed

- The manual's complete C program did not compile. `tcslog_write_open`
  takes eight arguments and the example passed seven, `cb` missing
  altogether and `&w` landing in its place; the function reference above it
  listed the same seven and stated outright that the callbacks are not an
  argument. Both were residue of the design before 0.2.8, when callbacks
  were process-wide and set separately: the `Callbacks from C` section was
  brought forward then and these two were not, so the document contradicted
  itself and the one piece of it a reader is most likely to compile was the
  wrong half.

  The example now defines the three callbacks and passes them, which is
  also what makes it demonstrate them: `send` reports the path it was
  handed, reached here through the close that hands over the segment file
  still open, so a handover is shown without writing enough to fill one.
  That `send` deliberately leaves the file where it is, against the
  contract, because the program reads the log back immediately afterwards
  -- a `send` that took the file away, which is what a real one must do,
  would leave the read with no segment files to find. The comment on it
  says so and points at the section stating the rule.

- `LogWrite::handler` and `LogWrite::handler_mut`, added in 0.2.8, were
  described in the manual's prose but absent from its list of the writer's
  methods and from the specification's, which that chapter opens by saying
  is the signatures the code must present. Both list them now, with why
  they borrow the handler rather than return it.

- The specification carried two `WriteCallbacks` sections once the trait
  took the name: the structure, under `Public Data Structures`, with
  `fn`-pointer fields and a default whose members do nothing, and the
  trait, under `The C Interface`, where the renamed `WriteHandler` section
  had been left. There is one now, under `Public Data Structures`, keeping
  the field comments that were the substantive part of the structure's;
  the C chapter points at it rather than restating it, the trait being
  Rust rather than ABI. `LogWrite::new`'s signature there had also kept
  `callbacks: WriteCallbacks`.

### Notes

- Two interfaces to the same library: the Rust API in the `tcslog` crate, and
  the C ABI in `tcslog-c`, whose header is `tcslog-c/include/tcslog.h`.
  crates.io carries the Rust crate alone, so the C side is built from a
  checkout; `make install` installs the header and both libraries, and `make
  uninstall` removes them.
- A runnable example for each: `tcslog/examples/sample.rs` through
  `bin/run-sample`, and `tcslog-c/examples/downlink.c` through
  `bin/run-capi-example`, each against a temporary directory it removes
  afterwards.
- User documentation is `docs/tcslog.rst`, which covers both interfaces, and
  the specification is `docs/tcslog-prompt.rst`.
